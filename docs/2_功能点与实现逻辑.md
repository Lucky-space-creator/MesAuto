## 一、订单管理

### 1.1 功能点

| 功能 | 接口 | 说明 |
|------|------|------|
| 分页查询订单 | `GET /api/order/page` | 支持多条件筛选（订单号、状态、日期范围、物料编码） |
| 创建订单 | `POST /api/order` | 含订单头 + 明细行 + BOM 物料清单 |
| 编辑订单 | `PUT /api/order/{id}` | 仅草稿/驳回状态可编辑 |
| 删除订单 | `DELETE /api/order/{id}` | 逻辑删除 |
| 提交审批 | `POST /api/order/{id}/submit` | 状态：草稿 → 审批中，自动匹配审批模板并启动审批链 |
| 订单下达 | `POST /api/order/{id}/release` | 审批通过后，状态：已下达 |
| 订单完成 | `POST /api/order/{id}/complete` | 全部入库后，状态：已完成 |
| 订单关闭 | `POST /api/order/{id}/close` | 强制终止 |
| 导入订单 | `POST /api/order/import` | Excel 批量导入 |
| 导出订单 | `GET /api/order/export` | Excel 导出当前筛选结果 |

### 1.2 实现逻辑

```
┌──────────────────────────────────────────────┐
│  创建订单                                      │
│  1. 校验必填字段（订单号、计划数量、日期）       │
│  2. OrderItem 校验物料是否存在                  │
│  3. OrderBom 校验 BOM 版本                     │
│  4. 插入 order + order_item（事务）             │
│  5. 返回 OrderDTO                             │
└──────────────────────────────────────────────┘
         │
         ▼ (提交审批)
┌──────────────────────────────────────────────┐
│  提交审批（模板驱动）                            │
│  1. 校验状态 = 草稿/驳回                       │
│  2. ApprovalRouter 自动匹配审批模板             │
│  3. 读取模板节点 → 创建 mes_approval_process    │
│  4. 写入审批记录 (approval_record)              │
│  5. 状态 → 审批中                              │
└──────────────────────────────────────────────┘
         │
         ▼ (审批通过)
┌──────────────────────────────────────────────┐
│  订单下达                                      │
│  1. 审批流程结束回调 → 更新状态                 │
│  2. 状态 → 已下达                              │
│  3. 自动触发排程（可选）                        │
└──────────────────────────────────────────────┘
         │
         ▼ (全部生产入库完成)
┌──────────────────────────────────────────────┐
│  订单完成                                      │
│  1. 查询关联入库单，校验数量是否达标            │
│  2. 状态 → 已完成                              │
│  3. 库存加总                                   │
└──────────────────────────────────────────────┘
```

### 1.3 关键校验规则

- **订单号全时段唯一**：租户维度下全局唯一（`UNIQUE(tenant_id, order_no)`）
- **计划数量 > 0**
- **计划开始日期 ≤ 计划结束日期**
- **BOM 物料必须在 `mes_material` 中存在且状态为启用**
- **状态流转**：`OrderStatusEnum` 枚举七种状态，内存状态机校验 `nextStates()`，拒绝非法跳转
  - DRAFT → APPROVING, CLOSED
  - APPROVING → RELEASED(通过), DRAFT(驳回), CLOSED
  - RELEASED → IN_PRODUCTION, CLOSED
  - IN_PRODUCTION → PENDING_STORAGE, CLOSED
  - PENDING_STORAGE → COMPLETED
  - COMPLETED → CLOSED
  - CLOSED → (终态，不可逆)

```
物料分类
┌────────────────────┐
│  MaterialCategory   │
│  ├─ id              │
│  ├─ parent_id       │  ← 自关联实现树形
│  ├─ category_name   │

│  └─ status          │
└────────────────────┘

物料主数据创建流程：
1. 校验编码唯一性（material_code + tenant_id）
2. 校验分类存在
3. 校验主/辅单位存在
4. 插入 mes_material

BOM 管理：
┌────────────────────┐       ┌────────────────────┐
│  Bom               │       │  BomItem            │
│  ├─ id              │  1:N  │  ├─ id              │
│  ├─ material_id     │◄─────┤  ├─ bom_id           │
│  ├─ version         │       │  ├─ child_material_id│
│  ├─ status          │       │  ├─ quantity         │
│  └─ effective_date  │       │  ├─ unit_id         │
└────────────────────┘       │  └─ scrap_rate      │
                             └────────────────────┘
BOM 创建：
1. 校验父物料存在
2. 批量插入 BomItem（子物料 + 用量）
3. 同一物料可多版本（仅一个启用）
```

## 三、仓储管理

### 3.1 功能点

| 功能 | 接口 | 说明 |
|------|------|------|
| 仓库/库位管理 | `/api/warehouse/**` | 仓库 + 库位（树形） |
| 库存查询 | `GET /api/inventory/page` | 按物料/仓库/库位分页 |
| 入库单管理 | `/api/inbound/**` | 创建/确认/取消入库 |
| 出库单管理 | `/api/outbound/**` | 创建/确认/取消出库 |
| 库存流水 | `GET /api/inventory/log` | 出入库明细记录 |

### 3.2 实现逻辑

```
入库流程：
┌──────────────┐     ┌──────────────┐     ┌──────────────┐
│  InboundOrder │     │ InboundItem  │     │  Inventory    │
│  (入库单头)    │────▶│ (入库明細)    │────▶│  (库存)        │
│  - order_no   │     │ - material_id│     │ - material_id │
│  - order_type │     │ - quantity   │     │ - quantity    │
│  - status     │     │ - warehouse  │     │ - warehouse   │
│  - source_order│    │ - location   │     │ - location    │
└──────────────┘     └──────────────┘     └──────────────┘

入库确认（事务）：
1. 校验入库单状态 = 待确认
2. 批量更新库存：新增或累加 quantity
3. 写入 inventory_log（出入库流水）
4. 更新入库单状态 = 已完成
5. 如果是生产入库，扣减订单待入库数量

出库流程同理，库存减少。

库存扣减使用 Redis 分布式锁：
  lockKey = "inv:{tenant}:{materialId}:{warehouseId}:{locationId}"
  1. tryLock(lockKey, 3s) → 防止超卖
  2. 查询库存 → 校验充足 → 扣减
  3. unlock(lockKey)
```

## 四、生产排程

### 4.1 功能点

| 功能 | 接口 | 说明 |
|------|------|------|
| 工位/工作中心管理 | `/api/workstation/**` | CRUD |
| 生产计划生成 | `POST /api/schedule/plan` | 从已下达订单拆解任务 |
| 生产任务查询 | `GET /api/schedule/task/page` | 按工位/日期/状态分页 |
| 任务开工 | `POST /api/schedule/task/{id}/start` | 状态变更 |
| 任务报工 | `POST /api/schedule/task/{id}/report` | 汇报产量/工时 |
| 任务完成 | `POST /api/schedule/task/{id}/complete` | 状态 → 已完成 |
| 任务暂停 | `POST /api/schedule/task/{id}/pause` | 暂停当前任务 |
| 任务恢复 | `POST /api/schedule/task/{id}/resume` | 恢复已暂停任务 |
| 排程甘特图数据 | `GET /api/schedule/gantt` | 前端可视化 |

### 4.2 实现逻辑

```
排程拆解（订单 + 工艺路线 → 任务）：
┌──────────────────┐       ┌──────────────────────┐
│  Order (已下达)    │       │  ProductionPlan       │
│  - order_no       │  1:1  │  - plan_no           │
│  - planned_qty    │──────▶│  - order_id          │
│  - route_id       │       │  - total_qty          │
└──────────────────┘       │  - status             │
        │                  └──────┬───────────────┘
        │ 引用工艺路线              │ 1:N 按工艺路线拆分
        ▼                         ▼
┌──────────────────────┐  ┌──────────────────────┐
│  ProcessRoute         │  │  ProductionTask       │
│  ProcessStep          │  │  - task_no            │
│  (工序1→工序2→...)    │  │  - plan_id            │
│  (顺序+并行+质检点)    │  │  - step_id → 工艺步骤  │
└──────────────────────┘  │  - material_id        │
                          │  - workstation_id     │
                          │  - planned_qty        │
                          │  - actual_qty         │
                          │  - status             │
                          └──────────────────────┘

排程生成算法（工艺路线驱动）：
1. 查已下达的订单列表
2. 对每个订单 → 读取 route_id 或物料默认工艺路线 (mes_process_route)
3. 按 step_seq 升序读取所有工序 (mes_process_step)
4. 逐工序映射工作中心 → 具体空闲工位
5. 顺序工序 → 建立任务依赖 (prev_task_id)
6. 并行工序 (parallel_group 相同) → 同一批生成，无依赖
7. 批量插入 production_task（关联 step_id）
8. 订单状态 → IN_PRODUCTION

报工逻辑：
1. 校验任务状态 = 生产中
2. actual_qty += 报工数量
3. 写入报工日志
4. 如果 actual_qty >= planned_qty → 自动完成
5. 订单维度累计完成率更新
```

### 5.1 功能点

| 功能 | 接口 | 说明 |
|------|------|------|
| 登录 | `POST /api/auth/login` | 用户名+密码 → JWT Token |
| 退出 | `POST /api/auth/logout` | 使 Token 失效 |

| 用户管理 | `/api/system/user/**` | CRUD + 启用/禁用 |
| 角色管理 | `/api/system/role/**` | CRUD + 分配权限 |
| 权限管理 | `/api/system/permission/**` | 菜单/按钮/接口权限树 |

### 5.2 实现逻辑

```
权限模型（标准 RBAC）：
┌──────────┐   N:N   ┌──────────┐   N:N   ┌──────────────┐
│  User    │◄───────►│  Role    │◄───────►│  Permission   │
│  - id    │         │  - id    │         │  - id         │
│  - username│       │  - code  │         │  - code       │
│  - password│       │  - name  │         │  - name       │
│  - status │         │  - status│         │  - type  │
│  - salt   │         └──────────┘         │    MENU|BTN|API│
└──────────┘                               │  - parent_id  │
                                           │  - url        │
                                           │  - perms      │
                                           └──────────────┘

鉴权流程（Shiro + JWT 无状态）：
1. 前端请求 Header 带 Authorization: Bearer {token}
2. JwtFilter 拦截 → 解析 Token 获取 userId
3. MesRealm.doGetAuthorizationInfo:
   - 查 sys_user_role → role_ids
   - 查 sys_role_permission → permission_codes
   - 构建 AuthorizationInfo(roles, permissions)
4. @RequiresPermissions("order:add") 匹配权限码

密码加密：SHA-256(userId + salt + rawPassword)

JWT Token 结构：
{
  "userId": 1,
  "username": "admin",
  "tenantId": "MES001",
  "iat": xxx,
  "exp": xxx + 7200   // 2小时过期
}
Token 存入 Redis(key = token:jwt:{token}, TTL = 2h) 用于退出时主动失效。
```

## 六、审批模块（动态审批模板驱动）

> **设计理念**：审批链不再是写死的 BPMN 文件，而是运营人员可在界面配置的**审批模板**。提交审批时系统自动根据业务类型/订单属性匹配模板，动态生成审批链。

### 6.1 功能点

| 功能 | 接口 | 说明 |
|------|------|------|
| 审批模板 CRUD | `/api/approval-template/**` | 创建/编辑/删除审批模板 |
| 审批节点管理 | `/api/approval-template/{id}/nodes` | 添加/删除/排序审批节点 |
| 模板启用/禁用 | `POST /api/approval-template/{id}/toggle` | 动态启用或停用 |
| 提交审批 | `POST /api/approval/{bizType}/{bizId}` | 自动匹配模板并启动审批链 |
| 待审批列表 | `GET /api/approval/todo` | 当前用户的待办审批任务 |
| 已审批列表 | `GET /api/approval/done` | 当前用户的已办审批任务 |
| 审批通过 | `POST /api/approval/{taskId}/approve` | 推进到下一节点 |
| 审批驳回 | `POST /api/approval/{taskId}/reject` | 退回发起人 |
| 转办 | `POST /api/approval/{taskId}/delegate` | 转给其他人审批 |
| 加签 | `POST /api/approval/{taskId}/add-sign` | 增加额外审批人 |
| 模板匹配预览 | `GET /api/approval/route/preview` | 预览某业务将走的审批链 |

### 6.2 实现逻辑

```
审批模板路由（自动选择合适的审批链）：
┌──────────────────────────────────────────────────────────┐
│  ApprovalRouter.selectTemplate(bizType, orderDTO)         │
│                                                           │
│  1. 查询 bizType 的启用模板，按 priority 排序               │
│  2. 检查模板的 condition_expr（如优先急单匹配）              │
│  3. 无条件模板作为 is_default 兜底                         │
│  4. 返回匹配的模板ID                                       │
│                                                           │
│  动态切换示例：                                             │
│  - 普通订单 → ORDER_NORMAL（部门主管→生产经理→总经理?）      │
│  - 急单     → ORDER_URGENT（生产经理→总经理，跳过部门主管）   │
│  - 返工单   → ORDER_REWORK（质量经理→总工）                  │
└──────────────────────────────────────────────────────────┘

审批链执行引擎（轻量级，不依赖 Activiti 流程部署）：
┌──────────────────────────────────────────────────────────┐
│  1. 提交审批 → 读取模板第一个节点 → 创建 mes_approval_task   │
│  2. 审批通过 → 推进到下一节点：                              │
│     ├─ 无后续节点 → 流程完成 → 回调业务状态                   │
│     ├─ 顺序节点 → 创建下一个待办                             │
│     └─ 并行节点 → 同时创建多个待办（会签）                    │
│  3. 审批驳回 → 所有待办取消 → 流程结束(REJECTED)             │
└──────────────────────────────────────────────────────────┘

审批记录（自建表，不依赖 Activiti 历史表）：
mes_approval_record:
  - template_id            使用的审批模板ID
  - node_id                当前审批节点ID
  - biz_type / biz_id      业务类型/ID
  - assignee               审批人
  - action                 动作(AGREE/REJECT/DELEGATE/ADD_SIGN)
  - comment                审批意见
  - create_time            审批时间
```

### 6.3 与 Activiti 的关系

Activiti 在本架构中作为**可选补充引擎**（方案 B 下不使用其流程定义功能）：
- 如果需要复杂的 BPMN 流程（子流程/边界事件/定时边界等），可将模板 XML 渲染后交给 Activiti
- 默认采用自定义轻量引擎，零重新部署，支持随时热切换模板

## 七、分页功能

### 7.1 统一封装

```java
// 请求
public class PageRequest<T> {
    private Integer pageNum = 1;    // 页码
    private Integer pageSize = 10;  // 每页条数（最大 100）
    private T condition;            // 查询条件 DTO
}

// 响应
public class PageResponse<T> {
    private Long total;            // 总记录数
    private Integer pageNum;       // 当前页
    private Integer pageSize;      // 每页条数
    private Integer totalPages;    // 总页数
    private List<T> records;       // 数据列表
}
```

### 7.2 实现方式

- Service 层使用 MyBatis-Plus `Page<T>` + 自定义 `QueryWrapper`/`LambdaQueryWrapper`
- Controller 层统一用 `R<PageResponse<T>>` 包裹
- 最大 `pageSize` 限制 100（防止深度分页打爆 MySQL）

## 八、导入导出

### 8.1 功能点

| 功能 | 接口 | 说明 |
|------|------|------|
| 下载导入模板 | `GET /api/excel/template/{bizType}` | 返回 Excel 模板文件 |
| 导入数据 | `POST /api/excel/import/{bizType}` | 上传 Excel，返回结果（成功/失败+错误行） |
| 导出数据 | `POST /api/excel/export/{bizType}` | 按条件导出为 Excel |

### 8.2 实现逻辑

```
导入流程（EasyExcel）：
1. 下载模板 → 用户填写 → 上传
2. EasyExcel 读取 → 逐行校验（字段格式/唯一性）
3. 错误收集到 List<ErrorRow>
4. 校验通过的行批量 INSERT (每 500 行一个 batch)
5. 返回 ImportResult(total, success, fail, errorDetails)

导出流程：
1. 接收查询条件
2. 分页查询数据（防止 OOM）
3. EasyExcel 流式写入
4. 上传到 MinIO，返回下载 URL
5. 记录导出日志

MinIO 文件路径规范：
  /mes/{tenant}/{bizType}/import/{yyyyMMdd}/{uuid}.xlsx
  /mes/{tenant}/{bizType}/export/{yyyyMMdd}/{uuid}.xlsx
```

## 九、ShardingSphere 分片策略

### 9.1 分片表

| 表 | 分片键 | 策略 | 说明 |
|-----|--------|------|------|
| `mes_order` | `create_time` | 按年分片 | `mes_order_2025`, `mes_order_2026`... |
| `mes_order_item` | `create_time` (绑定表) | 绑定 `mes_order` | 与订单同库 |
| `mes_inventory_log` | `create_time` | 按年分片 | 流水表数据量大 |
| `mes_approval_process` | `create_time` | 按年分片 | 审批流程实例 |
| `mes_approval_task` | `create_time` (绑定表) | 绑定 `mes_approval_process` | 审批待办任务 |
| `mes_approval_record` | `create_time` (绑定表) | 绑定 `mes_approval_process` | 审批记录与实例绑定 |

### 9.2 配置示例

```yaml
# sharding.yaml
dataSources:
  ds0:
    url: jdbc:mysql://localhost:3306/mescore?useSSL=false
    username: root
    password: root
rules:
- !SHARDING
  tables:
    mes_order:
      actualDataNodes: ds0.mes_order_$->{2024..2030}
      tableStrategy:
        standard:
          shardingColumn: create_time
          shardingAlgorithmName: order_year_alg
  shardingAlgorithms:
    order_year_alg:
      type: INTERVAL
      props:
        datetime-pattern: yyyy-MM-dd HH:mm:ss
        sharding-suffix-pattern: yyyy
        datetime-interval-amount: 1
        datetime-interval-unit: YEARS
        datetime-lower: 2024-01-01 00:00:00
```

## 十、Redis 缓存策略

| 缓存对象 | Key 模式 | TTL | 更新策略 |
|----------|----------|-----|----------|
| 用户 Token | `token:jwt:{token}` | 2h | 登录写入，退出删除 |
| 用户权限 | `perm:{userId}` | 30min | 登录写入，角色变更删除 |
| 物料信息 | `mat:{materialCode}` | 1h | 查无则写，变更删除 |
| 库存数量 | `inv:{materialId}:{warehouseId}` | 5min | 出入库后删除 |
| 分布式锁 | `lock:inv:{materialId}` | 3s | 业务完成释放 |
| 导入导出进度 | `task:{taskId}` | 24h | 异步任务轮询 |

## 十二、出库流程详解

```
出库流程：
1. 创建出库单（来源：生产领料 / 销售 / 调拨 / 报废）
2. 校验关联订单/物料是否存在
3. 状态 = PENDING（待确认）
4. 确认出库（事务）：
   a. 获取 Redis 锁 "lock:inv:{materialId}:{warehouseId}:{locationId}"
   b. 逐行校验库存充足（available = quantity - locked_quantity）
   c. 逐行扣减库存（quantity -= out_qty）
   d. 写入 inventory_log (DECREASE)
   e. 更新出库单状态 = COMPLETED
   f. 释放锁
5. 如果库存不足 → 状态保持 PENDING，返回错误明细
```

## 十四、工艺流程自定义编排

> **核心思想**：MES 中的"工艺路线"定义了产品的生产工序顺序和参数，不同产品的工艺路线不同。排程时不是简单地把 BOM 物料扔给工位，而是严格按照工艺路线一步步生成任务。

### 14.1 功能点

| 功能 | 接口 | 说明 |
|------|------|------|
| 工艺路线 CRUD | `/api/process-route/**` | 创建/编辑/删除/查询工艺路线 |
| 工序管理 | `/api/process-step/**` | 工序的排序、操作参数、关联工位类型 |
| 路线版本管理 | `POST /api/process-route/{id}/publish` | 发布新版本，旧版本自动失效 |
| 复制路线 | `POST /api/process-route/{id}/copy` | 从已有路线快速创建新路线 |
| 路线可视化 | `GET /api/process-route/{id}/flow` | 流程结构 JSON（前端 DAG 图渲染） |

### 14.2 数据模型

```
mes_process_route（工艺路线头）          mes_process_step（工序步骤）
┌──────────────────────────┐           ┌──────────────────────────────┐
│ id               BIGINT   │           │ id                   BIGINT   │
│ route_code       VARCHAR  │  1:N      │ route_id             BIGINT   │
│ route_name       VARCHAR  │◄─────────│ step_seq             INT      │ ← 顺序号
│ material_id      BIGINT   │           │ step_code            VARCHAR  │
│ version          VARCHAR  │           │ step_name            VARCHAR  │
│ status           VARCHAR  │           │ work_center_id       BIGINT   │ ← 执行的工作中心
│ effective_date   DATE     │           │ operation_type       VARCHAR  │ ← CUT/WELD/ASSEMBLY/QC/PACK
│ expired_date     DATE     │           │ standard_hours       DECIMAL  │ ← 标准工时
│ create_time      DATETIME │           │ setup_hours          DECIMAL  │ ← 准备工时
└──────────────────────────┘           │ prev_step_id         BIGINT   │ ← 前置工序(顺序执行)
                                       │ parallel_group       VARCHAR  │ ← 并行组(同组可并行)
                                       │ quality_check        TINYINT   │ ← 是否质检点
                                       │ parameters           JSON      │ ← 工艺参数(temperature,pressure...)
                                       └──────────────────────────────┘
```

**关键字段说明**：
- `prev_step_id`：标注前置工序，实现**顺序链**（工序 A → 工序 B → 工序 C）
- `parallel_group`：同一 `parallel_group` 内的工序可以**并行执行**（如"焊接 A"和"焊接 B"同时在两个工位执行）
- `parameters`：JSON 字段存储自定义工艺参数（温度、压力、转速等），支持**不同产品自定义不同参数**
- `version`：支持路线多版本，发布新版本旧版本自动失效

### 14.3 工序编排示例

```
产品 "电机总成" 的工艺路线 (V3.0)：

  [切割下料] ──────────────┐
  step_seq=1, work_center=切割中心  │
                          │ parallel_group="GROUP_A"
  [壳体焊接] ──────────────┘
  step_seq=2, work_center=焊接中心
         │
         ▼
  [转子装配] ──────────────┐
  step_seq=3, work_center=装配中心  │
                          │ parallel_group="GROUP_B"
  [定子装配] ──────────────┘
  step_seq=4, work_center=装配中心
         │
         ▼
  [总装] ───→ [电气测试] ───→ [外观检验] ───→ [包装入库]
  step=5      step=6(质检点)    step=7(质检点)   step=8
```

### 14.4 排程逻辑（工艺路线驱动）

```
改造后的排程流程：
┌─────────────────────────────────────────────────────────────┐
│  ProductionPlanService.generatePlan(orderId)                 │
│                                                              │
│  1. 读取订单的 material_id                                    │
│  2. 查询 material 绑定的 启用版工艺路线 (mes_process_route)     │
│  3. 按 step_seq 升序读取所有工序 (mes_process_step)            │
│  4. 逐工序生成 ProductionTask：                               │
│     ├─ 将工序的 work_center_id 映射到具体工位                  │
│     ├─ 将 standard_hours / setup_hours 写入任务              │
│     ├─ 质检点工序标注 quality_check_flag                      │
│     ├─ 并行工序 (parallel_group 相同) 同时生成                 │
│     └─ 顺序工序按 prev_step_id 建立依赖                       │
│  5. 批量插入 mes_production_task                              │
│  6. 订单状态 → IN_PRODUCTION                                  │
└─────────────────────────────────────────────────────────────┘
```

### 14.5 动态切换工艺路线

```
路由选择策略（按优先级）：
┌─────────────────────────────────────────────────────┐
│ 1. 订单指定的 route_id（最高优先级）                    │
│ 2. 物料绑定的最新启用版路线（默认）                      │
│ 3. 如果没有路线 → 降级为"BOM展开直排"（兼容老逻辑）       │
│                                                      │
│ 切换示例：                                             │
│ - 常规订单 → 走 "标准工艺 V3.0"                         │
│ - 急单/返工单 → 走 "简化工艺 V1.0"（跳过质检）           │
│ - 客户特殊需求 → 走 "客户定制工艺 V2.1"                  │
└─────────────────────────────────────────────────────┘

用户操作界面：
  /api/order/{id}/route → 下拉选择已有工艺路线 → 动态切换
```

## 十五、审批流程自定义编排

> **核心思想**：当前文档中的审批流程是硬编码的 `order-approval.bpmn`（部门主管→生产经理），无法满足不同业务/订单类型的审批差异。改造为**数据库驱动审批模板**，支持界面化配置和动态切换。

### 15.1 功能点

| 功能 | 接口 | 说明 |
|------|------|------|
| 审批模板 CRUD | `/api/approval-template/**` | 创建/编辑/删除模板 |
| 审批节点管理 | `/api/approval-template/{id}/nodes` | 模板内节点的增删改排序 |
| 模板发布/禁用 | `POST /api/approval-template/{id}/publish` | 启用该模板 |
| 模板预览 | `GET /api/approval-template/{id}/preview` | 预览该模板生成的审批链 |
| 动态路由 | `POST /api/approval/route` | 根据业务类型/条件选择模板 |

### 15.2 数据模型

```
mes_approval_template（审批模板）          mes_approval_node（模板节点）
┌─────────────────────────────┐           ┌──────────────────────────────┐
│ id                  BIGINT   │           │ id                    BIGINT  │
│ template_code       VARCHAR  │  1:N      │ template_id           BIGINT  │
│ template_name       VARCHAR  │◄─────────│ node_seq              INT     │ ← 审批顺序
│ biz_type            VARCHAR  │           │ node_name             VARCHAR │ ← "部门主管审批"
│ biz_category        VARCHAR  │           │ assignee_type         VARCHAR │ ← ROLE/SPECIFIC/DYNAMIC
│ description         VARCHAR  │           │ assignee_id           BIGINT  │ ← 具体审批人/角色ID
│ status              VARCHAR  │           │ assignee_expr         VARCHAR │ ← 动态表达式
│ priority            INT      │           │ condition_expr        VARCHAR │ ← 条件表达式
│ is_default          TINYINT  │           │ timeout_hours         INT     │ ← 超时时间
│ create_time         DATETIME │           │ allow_delegate        TINYINT  │ ← 是否允许转办
└─────────────────────────────┘           │ allow_add_sign        TINYINT  │ ← 是否允许加签
                                          └──────────────────────────────┘
```

**关键字段说明**：

| 字段 | 用途 | 示例 |
|------|------|------|
| `assignee_type` | 审批人来源 | `ROLE`=按角色 / `SPECIFIC`=指定人 / `DYNAMIC`=动态表达式 |
| `assignee_expr` | 动态审批人 | `${order.departmentManager}` → 取订单所属部门的主管 |
| `condition_expr` | 节点跳过条件 | `${order.totalAmount < 10000}` → 小额订单跳过此节点 |
| `condition_expr` | 分支条件 | `${order.priority == 'HIGH'}` → 急单走快速通道 |
| `node_seq` | 排序 + 并行标识 | `1`, `2a`(并行A), `2b`(并行B), `3` → a/b 同级可会签 |

### 15.4 动态切换实现逻辑

```
审批模板路由决策（运行时选择哪个模板）：
┌──────────────────────────────────────────────────────────┐
│  ApprovalRouter.selectTemplate(bizType, orderDTO)         │
│                                                           │
│  1. 查询 bizType 的所有启用模板，按 priority 排序            │
│  2. 逐一检查 "模板适用范围条件" (template_condition_expr)     │
│     ├─ 无条件的 → 最低优先级，兜底使用                        │
│     ├─ 有条件的 → 用 Aviator/MVEL 表达式引擎求值             │
│     │   e.g., order.priority == 'HIGH' &&                  │
│     │         order.totalAmount > 10000                    │
│     └─ 一旦命中即返回模板ID                                  │
│  3. 无命中 → 返回 is_default=1 的模板                       │
│                                                           │
│  切换场景：                                                 │
│  - 普通订单 → ORDER_NORMAL (部门主管→生产经理→总经理?)       │
│  - 急单     → ORDER_URGENT (生产经理→总经理)                  │
│  - 返工单   → ORDER_REWORK (质量经理→总工)                    │
│  - 委外订单 → ORDER_OUTSOURCE (采购经理→总经理)               │
└──────────────────────────────────────────────────────────┘

审批流程执行（模板 → 审批链 → Activiti 运行时）：
┌──────────────────────────────────────────────────────────┐
│  ApprovalService.submit(bizType, bizId)                   │
│                                                           │
│  1. ApprovalRouter.selectTemplate() → 选中模板             │
│  2. 读取模板节点列表 (mes_approval_node)，按 node_seq 排序   │
│  3. 遍历节点：                                              │
│     ├─ 检查 condition_expr → 决定是否跳过                   │
│     ├─ 检查 assignee_type → 解析审批人                      │
│     │   ROLE → 查 sys_user_role 获取角色成员               │
│     │   SPECIFIC → 直接用 assignee_id                     │
│     │   DYNAMIC → 执行 SpEL/Aviator 表达式                 │
│     ├─ 并行节点 (同 node_seq 前缀的节点) → 会签              │
│     └─ 顺序节点 → 串行审批                                  │
│  4. 将模板渲染为 Activiti 节点链 → 启动流程实例              │
│  5. 写入 approval_record (记录使用的模板ID)                  │
│  6. 回调业务状态 (如订单 APPROVING)                         │
└──────────────────────────────────────────────────────────┘
```

### 15.5 两种实现方案对比

| 维度 | 方案A：动态生成BPMN | 方案B：自定义轻量引擎 ⭐推荐 |
|------|---------------------|------------------------------|
| 实现 | 模板 → 渲染 BPMN XML → 调用 Activiti API 部署和启动 | 模板节点直接驱动状态机，不再依赖 Activiti 流程定义 |
| 优势 | 复用 Activiti 能力、流程图可视化 | 零重新部署、查询性能高、节点自由扩展 |
| 劣势 | 每次修改模板需重新部署流程定义、并发版本管理复杂 | 需自建任务领取/完成逻辑 |
| 适用 | 审批链变化不频繁、需要复杂 BPMN 能力 | **审批链频繁变化、需要极简热切换** |

**推荐方案 B**：审批模板节点直接驱动，Activiti 仅保留作为可选引擎。实现如下：

```java
// 核心服务伪代码
@Service
public class ApprovalEngineService {

    // 提交审批 → 创建第一个待办任务
    public void submit(Long templateId, String bizType, Long bizId) {
        val nodes = approvalNodeMapper.selectByTemplateId(templateId);
        val firstNode = nodes.get(0);
        // 解析审批人
        String assignee = resolveAssignee(firstNode);
        // 创建待办任务
        mesApprovalTask.setTemplateId(templateId);
        mesApprovalTask.setNodeId(firstNode.getId());
        mesApprovalTask.setAssignee(assignee);
        // 发出通知...
    }

    // 审批通过 → 推进到下一个节点
    public void approve(Long taskId, String comment) {
        val task = getTask(taskId);
        val nextNode = getNextNode(task.getTemplateId(), task.getNodeSeq());
        if (nextNode == null) {
            // 流程结束 → 回调业务
            bizCallbackService.onApproved(task.getBizType(), task.getBizId());
        } else {
            // 推进到下一节点
            createNextTask(task, nextNode);
        }
    }
}
```
